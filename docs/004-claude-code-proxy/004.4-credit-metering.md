# 004.4 - Credit Metering

**Phase 004: Claude Code Proxy** -- Sub-doc 4 of 4: Per-request credit reserve/settle for proxy.

> See also: [004.1 Anthropic Proxy](./004.1-anthropic-proxy.md) | [004.2 API Tokens](./004.2-api-tokens.md) | [004.3 Settings UI](./004.3-settings-ui.md)

## Overview

Per-request credit reserve and settle flow for the stateless `/v1/messages` proxy. Different from web chat (Phase 2): no session DO, no cumulative budget tracking. Each request independently reserves credits upfront, then settles based on actual `usage` from the Claude API response.

## Context & Background

Phase 2's credit engine ([002.3](../002-core-session/002.3-credit-engine.md)) handles session-scoped reserve/settle with a single settlement at session end. The proxy flow is simpler: reserve per-request, settle per-request. Same DB tables, same credit formulas, different lifecycle.

## Goals

- Per-request credit reserve from `max_tokens` estimate
- Per-request credit settle from actual `usage` in Claude API response
- Reject requests with insufficient credits (Anthropic error format)
- Usage logging via `USAGE_LOG_QUEUE` after each request
- Handle edge cases: interrupted streams, provider key invalid mid-stream

## Non-Goals

- Session-based budget tracking (web chat handles this)
- Credit purchase/top-up
- Per-token rate limiting (Phase 5)

---

## 1. Web Chat vs Proxy Credit Flow

| Aspect | Web Chat (Phase 2) | Claude Code Proxy (Phase 4) |
|--------|--------------------|-----------------------------|
| Lifecycle | Session (many requests) | Single request |
| Reserve timing | Session start (worst-case budget) | Request start (from `max_tokens`) |
| Settle timing | Session end (once) | Stream end (per request) |
| State | SessionAgent DO tracks cumulative usage | Stateless, no persistent state |
| Budget enforcement | `maxTokensBudget` on session | `max_tokens` on each request |
| Credit source | `reserveCredits()` from 002.3 | `reserveCreditsForRequest()` (this doc) |

## 2. Reserve Logic

File: `apps/data-service/src/hono/services/proxy-credit-service.ts`

### 2.1 Types

```ts
interface ReserveResult {
  ok: true
  creditsReserved: number
  rollback: () => Promise<void>
}

interface ReserveFailure {
  ok: false
  available: number
}

type ReserveOutcome = ReserveResult | ReserveFailure
```

### 2.2 Reserve Implementation

```ts
import { getDb } from "@repo/data-ops/database/setup"
import { creditBalance } from "@repo/data-ops/drizzle/schema"
import { eq, sql } from "drizzle-orm"

export async function reserveCreditsForRequest(
  userId: string,
  estimatedCredits: number
): Promise<ReserveOutcome> {
  const db = getDb()

  // Optimistic lock: atomically check + reserve
  const result = await db
    .update(creditBalance)
    .set({
      available: sql`${creditBalance.available} - ${estimatedCredits}`,
      reserved: sql`${creditBalance.reserved} + ${estimatedCredits}`,
    })
    .where(
      sql`${creditBalance.userId} = ${userId}
          AND ${creditBalance.available} >= ${estimatedCredits}`
    )
    .returning({ available: creditBalance.available })

  if (result.length === 0) {
    // Fetch actual balance for error message
    const [bal] = await db
      .select({ available: creditBalance.available })
      .from(creditBalance)
      .where(eq(creditBalance.userId, userId))

    return { ok: false, available: bal?.available ?? 0 }
  }

  // Rollback function for error paths (provider key invalid, upstream error)
  const rollback = async () => {
    await db
      .update(creditBalance)
      .set({
        available: sql`${creditBalance.available} + ${estimatedCredits}`,
        reserved: sql`${creditBalance.reserved} - ${estimatedCredits}`,
      })
      .where(eq(creditBalance.userId, userId))
  }

  return { ok: true, creditsReserved: estimatedCredits, rollback }
}
```

The `rollback` closure captures `estimatedCredits` and `userId` so the caller can undo the reservation without tracking those values.

## 3. Settle Logic

### 3.1 Types

```ts
interface SettleInput {
  userId: string
  providerId: string
  poolId: string
  creditsReserved: number
  inputTokens: number
  outputTokens: number
  creditsPerInputKToken: number
  creditsPerOutputKToken: number
}
```

### 3.2 Settle Implementation

```ts
import { creditLedger } from "@repo/data-ops/drizzle/schema"
import { calculateCreditsUsed } from "./token-meter"
import { ulid } from "ulid"

export async function settleCreditsForRequest(
  input: SettleInput
): Promise<void> {
  const db = getDb()

  const actualCredits = calculateCreditsUsed(
    input.inputTokens,
    input.outputTokens,
    input.creditsPerInputKToken,
    input.creditsPerOutputKToken
  )

  const refund = input.creditsReserved - actualCredits

  await db.transaction(async (tx) => {
    // Consumer: release reserved, refund excess
    await tx
      .update(creditBalance)
      .set({
        reserved: sql`${creditBalance.reserved} - ${input.creditsReserved}`,
        available: sql`${creditBalance.available} + ${refund}`,
      })
      .where(eq(creditBalance.userId, input.userId))

    // Consumer ledger entry
    const [consumerBal] = await tx
      .select({ available: creditBalance.available })
      .from(creditBalance)
      .where(eq(creditBalance.userId, input.userId))

    await tx.insert(creditLedger).values({
      id: ulid(),
      userId: input.userId,
      amount: -actualCredits,
      type: "consumer_spend",
      balanceAfter: consumerBal.available,
    })

    // Provider: earn credits
    await tx
      .update(creditBalance)
      .set({
        available: sql`${creditBalance.available} + ${actualCredits}`,
      })
      .where(eq(creditBalance.userId, input.providerId))

    // Provider ledger entry
    const [providerBal] = await tx
      .select({ available: creditBalance.available })
      .from(creditBalance)
      .where(eq(creditBalance.userId, input.providerId))

    await tx.insert(creditLedger).values({
      id: ulid(),
      userId: input.providerId,
      amount: actualCredits,
      type: "provider_earning",
      balanceAfter: providerBal.available,
    })
  })
}
```

Same transactional pattern as Phase 2 ([002.3](../002-core-session/002.3-credit-engine.md)), but without session ID (proxy requests are sessionless).

## 4. Credit Estimation

The reserve amount is estimated from `max_tokens` (worst case: all output):

```
estimatedCredits = ceil((max_tokens / 1000) * creditsPerOutputKToken)
```

This uses the existing `calculateCreditsUsed()` from `token-meter.ts` with `inputTokens = 0`:

```ts
// from services/token-meter.ts (Phase 2)
calculateCreditsUsed(0, maxTokens, pool.creditsPerInputKToken, pool.creditsPerOutputKToken)
```

Input tokens are unknown at request time (depends on conversation length sent by Claude Code), so only output tokens are estimated. Actual input token cost is charged at settle time.

## 6. Error Response Format

All credit-related errors use Anthropic JSON error format so Claude Code handles them natively:

### Insufficient Credits

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "Insufficient credits (available: 42, estimated: 150). Top up at https://aigent.community/credits"
  }
}
```

HTTP 400. Uses `invalid_request_error` type (not `permission_error`) because the request itself is valid, just unfunded.

### Pool Inactive

```json
{
  "type": "error",
  "error": {
    "type": "not_found_error",
    "message": "Pool not found or inactive"
  }
}
```

HTTP 404.

### No Pool Configured

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "No pool configured. Set default_pool_id on your API token or pass X-Pool-Id header."
  }
}
```

HTTP 400.

## 7. Edge Cases

### 7.1 Stream Interrupted Mid-Response

If the connection drops before `message_delta` (which contains final `usage`):

- `outputTokens` will be 0 or partial
- Settlement runs in the `finally` block of the pump function, so it always executes
- Consumer is charged for whatever tokens were actually reported
- If `outputTokens = 0`, consumer gets full refund (reserve - 0 = reserve)
- Anthropic API may still bill the provider for partial responses

### 7.2 Provider Key Invalid Mid-Stream

If Claude API returns 401:

- Request never starts streaming (401 is returned before SSE begins)
- Reserve is rolled back via `reserveResult.rollback()`
- Pool auto-paused, provider reputation decremented -0.2
- Error returned in Anthropic format

### 7.3 Settle Fails (DB Error)

If the settlement transaction fails:

- Credits remain in `reserved` state (not lost)
- Consumer's `available` is temporarily lower than it should be
- Needs manual intervention or a sweep job to reconcile
- This is the safe direction: over-reserve, never over-spend

### 7.4 Actual Cost Exceeds Estimate

Possible if `input_tokens` is large (long conversation). The estimate only accounts for `max_tokens` output. Actual cost = input + output.

- If `actualCredits > creditsReserved`, the `refund` variable is negative
- The settle transaction still works: `available + negative_refund` = `available - abs(refund)`
- Consumer's available balance decreases further
- Edge case: available could go negative. Acceptable in MVP (consumer already authorized the request)

- [ ] `reserveCreditsForRequest` atomically checks + reserves (optimistic lock)
- [ ] Insufficient credits returns `{ ok: false, available }` (no throw)
- [ ] Reserve returns `rollback()` closure for error paths
- [ ] `settleCreditsForRequest` runs in single `db.transaction()`
- [ ] Settlement: consumer charged `actualCredits`, refunded `reserved - actual`
- [ ] Settlement: provider earns `actualCredits`
- [ ] Ledger entries created for both consumer and provider
- [ ] Usage enqueued to `USAGE_LOG_QUEUE` after settlement
- [ ] Stream interruption: settlement runs in `finally` block
- [ ] Provider key 401: reserve rolled back, pool paused
- [ ] All credit errors use Anthropic JSON error format
- [ ] Credit formula: `ceil((input/1000)*inputRate + (output/1000)*outputRate)`
